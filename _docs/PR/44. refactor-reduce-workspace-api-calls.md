## 2. 변경 배경 및 목표
- **변경 전 상태:** 워크스페이스 서버 렌더링이 Log 목록을 조회한 뒤 모든 Log 상세를 다시 조회하고, Output도 상태별 목록 3회와 모든 상세를 추가 조회했습니다. 전체 스냅샷이 필요하지 않은 목록·작성·편집 화면도 Link, Todo, Output, Memory, Working Brief까지 공통으로 불러왔습니다. 백엔드 Output 목록은 Output마다 Task/Log 연결을 각각 조회했습니다.
- **문제/필요성:** 워크스페이스의 Log 수 `L`, Output 수 `O`가 증가할수록 HTTP 상세 호출이 `L + O`회 추가됐고, Output 연결 Repository 조회도 `2O`회 증가했습니다. 모든 fetch가 `cache: "no-store"`이므로 이 요청들은 응답 캐시에 흡수되지 않고 백엔드 부하로 이어졌습니다.
- **이번 PR의 목표:** 목록 응답은 요약 데이터로 사용하고 선택한 항목만 상세 조회하며, 화면별로 필요한 워크스페이스 데이터만 불러옵니다. Output 연결 정보는 목록 응답과 배치 조회로 제공해 프론트 HTTP fan-out과 백엔드 N+1을 함께 제거합니다.

## 3. 주요 구현 내용 및 동작 방식

### A. Log·Output 상세 지연 조회
- **관련 위치/대상:** `frontend/src/03_entities/workspace/api/workspaceApi.ts`, Log/Output 상세·편집 Feed
- **변경 전 상황:** Log 목록 이후 Log 수만큼 상세 API를 호출했고, Output은 상태별 목록 3회 이후 Output 수만큼 상세 API를 호출했습니다.
- **변경한 내용:** 목록 응답을 화면 데이터로 바로 매핑하고 `getWorkspaceLog`, `getWorkspaceOutput`으로 선택한 ID의 상세만 조회하도록 분리했습니다. Output 목록 호출은 상태 필터 없는 단일 요청으로 통합했습니다.
- **변경 후 동작:** 목록·전체 화면에서는 Log/Output 상세 반복 호출이 발생하지 않습니다. Log 편집과 Output 상세는 선택 항목 1건만 추가 조회합니다.
- **구현 흐름:**
  1. Task/Log/Output 목록 응답을 요약 모델로 매핑합니다.
  2. 상세 본문이 필요한 Feed가 선택된 ID의 상세 API를 호출합니다.
  3. 구버전 백엔드 응답에 `taskIds`, `logIds`가 없어도 빈 배열로 처리해 독립적인 배포 순서를 허용합니다.
- **바뀌는 데이터/상태:** Output 목록 응답에 `taskIds`, `logIds`가 추가됩니다. 기존 `taskCount`, `logCount`는 유지됩니다.
- **영향 범위:** Workspace Dashboard, Log 목록/상세/편집, Output 목록/상세/작성, Task 상세의 연결 Output 표시

### B. Output 연결 Repository 배치 조회
- **관련 위치/대상:** `backend` Output Service, Mapper, DTO, Task/Log 연결 Repository
- **변경 전 상황:** `getOutputs`가 각 Output마다 `findAllByOutputId`를 Task와 Log에 각각 실행했습니다.
- **변경한 내용:** 전체 Output ID를 수집하고 `findAllByOutputIdIn`으로 Task/Log 연결을 각각 한 번에 조회한 뒤 Output ID로 그룹화합니다.
- **변경 후 동작:** Output 개수와 관계없이 연결 Repository 호출이 최대 2회로 고정됩니다. Output이 없으면 연결 조회 없이 즉시 빈 목록을 반환합니다.
- **구현 흐름:**
  1. Workspace의 Output 목록과 ID를 조회합니다.
  2. Task/Log 연결을 ID 묶음으로 각각 조회합니다.
  3. Output별 ID 목록과 count를 함께 응답합니다.
- **바뀌는 데이터/상태:** DB schema 변경은 없고 Output 목록 JSON 응답 필드만 추가됩니다.
- **영향 범위:** `GET /workspaces/{workspaceId}/outputs`, Output 목록을 사용하는 Web/CLI API 소비자

### C. 화면별 경량 워크스페이스 로더
- **관련 위치/대상:** Workspace API loader와 Activity, Home, Task, Log, Output, Planner Feed
- **변경 전 상황:** Task/Log 탐색만 필요한 화면도 전체 Workspace snapshot을 조회했습니다.
- **변경한 내용:** Workspace + Task + Log만 조회하는 `loadWorkspaceNavigationPageData`를 추가하고 목록·작성·편집·Activity·Planner·App Chrome에 적용했습니다.
- **변경 후 동작:** 경량 화면은 Link, Todo, Output, Memory, Working Brief를 호출하지 않습니다. Dashboard, Graph, Memory, Task Detail, Outputs List처럼 전체 데이터가 필요한 화면은 기존 전체 loader를 유지합니다.
- **영향 범위:** 로그인 사용자의 Workspace 관련 서버 렌더링 API 호출 수

### D. 호출 수 비교 및 레이트리미트 후속 설계
- **관련 위치/대상:** `_docs/tasks/2026-07-14_reduce-workspace-api-calls.md`, `_docs/plan/2026-07-14_rate-limit-scope.md`
- **변경 전 상황:** 호출 감소 효과와 외부 남용 방어 범위가 수치 및 단계별 정책으로 정리돼 있지 않았습니다.
- **변경한 내용:** 데이터 규모별 호출 수 공식, 화면별 전후 비교, Repository 호출 비교를 기록했습니다. Nginx 비상 상한과 Redis 기반 사용자·Workspace·Device·Token 정책의 단계별 적용 범위를 별도 Plan으로 설계했습니다.
- **변경 후 동작:** 중규모 예시 `(Task 100 / Log 100 / Output 20 / Memory 50)`에서 전체 loader는 134회에서 12회, 경량 loader는 5회로 줄어드는 근거를 리뷰할 수 있습니다. 레이트리미트는 이번 PR에서 구현하지 않습니다.
- **영향 범위:** 후속 성능 관측, 레이트리미트 Task 분해 및 운영 rollout 계획
