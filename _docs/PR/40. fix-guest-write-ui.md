## 2. 변경 배경 및 목표
- **변경 전 상태:** 비로그인 사용자에게 게시글 댓글 작성기, Suggest 생성 링크, Suggest Discussion 작성기가 표시됐고 `/suggestions/new` 주소로 작성 화면에 직접 접근할 수 있었습니다. 피드 게시글 제목은 다른 화면과 달리 Georgia serif 폰트를 강제로 사용했습니다.
- **문제/필요성:** 실제 API 요청은 백엔드 인증으로 거절되더라도 게스트 화면에 실행할 수 없는 작성 UI가 노출돼 사용자에게 잘못된 기대를 줬습니다. 피드 제목의 별도 serif 지정도 전역 타이포그래피와 일관되지 않았습니다.
- **이번 PR의 목표:** 게스트 화면은 공개 콘텐츠 조회에 필요한 UI만 제공하고, 작성·변경 진입점은 로그인 사용자에게만 렌더링합니다. 피드 제목은 전역 폰트를 상속하도록 통일합니다.

---

## 3. 주요 구현 내용 및 동작 방식

### A. 비로그인 작성 UI 차단
- **관련 위치/대상:** 공개 게시글, 댓글 섹션, Suggest 목록·상세·작성 페이지, 좋아요 버튼
- **변경 전 상황:** 로그인 여부와 무관하게 댓글 composer, `+ New suggest`, Suggest Discussion composer가 렌더링됐고 좋아요 버튼도 클릭 가능한 형태로 표시됐습니다.
- **변경한 내용:** 서버에서 확인한 로그인 여부를 명시적인 boolean prop으로 전달해 댓글·Discussion 작성기와 Suggest 생성 링크를 조건부 렌더링했습니다. 게스트의 좋아요는 클릭 버튼 대신 읽기 전용 집계로 표시합니다.
- **변경 후 동작:** 게스트는 기존 댓글·Suggest·좋아요 수를 조회할 수 있지만 작성·수정·삭제·좋아요 변경 UI는 볼 수 없습니다. 로그인 사용자는 기존 기능을 그대로 사용할 수 있습니다.
- **구현 흐름:**
  1. 공개 페이지에서 `getUser()` 결과를 capability prop으로 변환합니다.
  2. 각 UI 컴포넌트가 capability가 참일 때만 변경 UI를 렌더링합니다.
- **바뀌는 데이터/상태:** 게스트 화면의 DOM과 직접 접근 시 라우팅 결과만 변경되며 API·DB 계약은 변경하지 않습니다.
- **영향 범위:** 공개 게시글 상세, 댓글, Suggest 목록·상세·Discussion, 좋아요 표시

### B. Suggest 작성 경로 직접 접근 방어
- **관련 위치/대상:** `frontend/app/[username]/posts/[postSlug]/suggestions/new/page.tsx`
- **변경 전 상황:** 게스트가 작성 링크를 직접 입력하면 Suggest editor가 렌더링됐습니다.
- **변경한 내용:** 서버 컴포넌트에서 로그인과 온보딩 상태를 확인한 뒤 게스트를 해당 게시글의 Suggest 목록으로 리다이렉트합니다. 인증이 확인된 이후에만 workspace chrome과 작성 action을 구성합니다.
- **변경 후 동작:** 비로그인 사용자는 Suggest editor를 직접 열 수 없고 목록 화면으로 돌아갑니다.
- **바뀌는 데이터/상태:** 게스트의 `/suggestions/new` 응답이 작성 화면에서 목록 리다이렉트로 변경됩니다.
- **영향 범위:** 공개 Suggest 신규 작성 경로

### C. 피드 제목 폰트 통일
- **관련 위치/대상:** `frontend/src/01_widgets/home-feed/ui/FeedArticleCard.tsx`
- **변경 전 상황:** 피드 게시글 제목에 `[font-family:Georgia,serif]`가 별도로 지정돼 전역 폰트와 다른 형태로 표시됐습니다.
- **변경한 내용:** 컴포넌트의 Georgia 강제 지정을 제거했습니다.
- **변경 후 동작:** 피드 제목이 애플리케이션 전역 폰트를 상속합니다.
- **영향 범위:** 홈 피드 게시글 카드 제목

## 5. 테스트 및 검증 방법
- **검증 환경:** macOS, Node.js 25.2.1, pnpm 10.26.2, Next.js 16.1.6, Playwright Chromium
