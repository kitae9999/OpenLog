## 2. 변경 배경 및 목표
- **변경 전 상태:** 워크스페이스가 하나의 `repo_full_name`만 보유했고, MCP를 설치해도 현재 프로젝트와 워크스페이스의 연결이나 에이전트 기록 기준은 자동으로 제공되지 않았습니다.
- **문제/필요성:** 에이전트가 OpenLog를 사용하려면 별도 지침 파일이 필요했고, 프로젝트별 기록 방식과 여러 저장소를 사용하는 워크스페이스를 표현할 수 없었습니다.
- **이번 PR의 목표:** MCP 설치와 프로젝트 연결을 분리하고, 워크스페이스 Agent Guide와 프로젝트별 Capture Mode를 통해 에이전트가 일관된 기준으로 OpenLog를 사용하도록 합니다.

## 3. 주요 구현 내용 및 동작 방식

### A. Workspace Agent Guide와 프로젝트 연결 모델
- **관련 위치/대상:** Backend Flyway migration, workspace guide/project domain·service·API, frontend API model
- **변경 전 상황:** 워크스페이스에 단일 GitHub 저장소 문자열만 저장했습니다.
- **변경한 내용:** `workspace_agent_guides`와 `workspace_projects`를 추가하고 기존 repository 데이터를 프로젝트 연결로 이관했습니다. Guide 조회·수정, 프로젝트 CRUD·resolve, 통합 agent context API를 추가했습니다.
- **변경 후 동작:** 한 워크스페이스에 여러 Git 프로젝트를 연결하고, 프로젝트마다 `AUTO`, `ASK`, `EXPLICIT` Capture Mode를 설정할 수 있습니다. 기본값은 `ASK`입니다.
- **구현 흐름:**
  1. 기존 워크스페이스에는 기본 영어 Guide를 생성하고 정규화된 repository key 기준으로 프로젝트를 이관합니다.
  2. owner 권한을 확인한 API가 최신 Guide revision, 프로젝트, 워크스페이스, Capture Mode를 통합 context로 반환합니다.
- **바뀌는 데이터/상태:** `workspaces.repo_full_name`은 이관 후 제거되며 Guide content/revision과 프로젝트 연결 상태가 별도 테이블에 저장됩니다.
- **영향 범위:** Backend DB schema와 Workspace API 응답, CLI·MCP·Frontend의 repository 사용처

### B. `setup`/`init` 분리와 MCP session context
- **관련 위치/대상:** `packages/openlog-cli`, MCP server/tool definitions
- **변경 전 상황:** MCP 설치만으로는 현재 프로젝트를 식별하거나 워크스페이스별 지침을 에이전트에 전달할 수 없었습니다.
- **변경한 내용:** `openlog setup`은 로그인·MCP 등록만 담당하도록 유지하고, Git 프로젝트에서 실행하는 대화형 `openlog init`을 추가했습니다. MCP initialize instructions와 읽기 Tool `start_openlog_session`도 추가했습니다.
- **변경 후 동작:** Git remote가 있으면 기존 연결을 탐색하고, remote가 없으면 로컬 프로젝트로 연결합니다. 선택한 workspace와 Capture Mode는 서버에 저장하고 프로젝트 ID는 추적되지 않는 `.git/config`에 기록합니다.
- **구현 흐름:**
  1. `openlog init`이 Git root·remote·기존 project ID를 확인하고 workspace 및 Capture Mode 선택을 받은 뒤 서버 연결을 생성하거나 갱신합니다.
  2. 에이전트는 실질적인 작업 전에 `start_openlog_session(projectPath)`을 호출해 최신 Guide와 Capture Mode를 받고, 미초기화·stale 연결이면 재초기화 안내를 반환받습니다.
- **바뀌는 데이터/상태:** 로컬 Git config의 `openlog.projectId`, 서버의 workspace project binding과 Capture Mode
- **영향 범위:** CLI onboarding, MCP initialize 응답, Task·Log·Output 생성·수정 Tool description 및 권한별 Tool 노출

### C. Agent Settings와 첫 사용 안내 UI
- **관련 위치/대상:** `/settings/workspaces/{workspaceId}/agent`, Dashboard·Manage workspace UI
- **변경 전 상황:** 워크스페이스 설정에서 단일 repository만 입력할 수 있었고, 에이전트 가이드나 프로젝트별 정책을 관리할 화면이 없었습니다.
- **변경한 내용:** Markdown Write/Preview Guide 편집기, revision·저장 상태, 연결 프로젝트 목록, Capture Mode 변경과 연결 해제 기능을 추가했습니다. Dashboard와 Manage에 진입점을 연결하고 새 워크스페이스 사용자에게 MCP 설정 및 Agent Guide 안내를 표시합니다. 사이드바는 경로별 prop 없이도 현재 또는 저장된 workspace를 해석해 Agent Guide 링크를 항상 제공합니다.
- **변경 후 동작:** 사용자는 웹에서 워크스페이스의 단일 Guide를 수정하고 각 Remote/Local Git project의 기록 방식을 관리할 수 있습니다. 새 연결은 화면에서 `openlog init` 명령으로 안내합니다.
- **구현 흐름:**
  1. Agent Settings 진입 시 Guide와 프로젝트 목록을 조회하고 Markdown 편집·미리보기를 제공합니다.
  2. 프로젝트별 Capture Mode 변경과 연결 해제를 즉시 API에 반영하며, 프로젝트 수에 맞춰 Workspace repository 표시를 전환합니다.
- **바뀌는 데이터/상태:** Guide revision·updatedAt, 프로젝트별 Capture Mode, MCP/Agent Guide 안내 dismiss 상태(localStorage)
- **영향 범위:** Workspace 생성·수정·목록·Dashboard UI, 공통 scrollbar와 Agent Guide editor 표현

### D. Agent onboarding 문서
- **관련 위치/대상:** Root·CLI README, 영문·한글 MCP Guide, 구현 계획 문서
- **변경 전 상황:** MCP 설치와 프로젝트 연결, Capture Mode, `.git/config` binding이 구분되어 설명되지 않았습니다.
- **변경한 내용:** `setup` 후 프로젝트별 `init`을 실행하는 흐름과 Workspace Guide, 세 가지 Capture Mode, Agent Settings 사용법을 문서화했습니다.
- **변경 후 동작:** 사용자는 설치와 프로젝트 연결의 차이 및 에이전트가 Guide를 불러오는 과정을 문서만으로 확인할 수 있습니다.
- **구현 흐름:**
  1. 전역 MCP 설정은 프로젝트 경로를 탐색하지 않습니다.
  2. 각 Git 프로젝트에서 `npx @openloghq/cli init`을 실행해 명시적으로 연결합니다.
- **바뀌는 데이터/상태:** 없음
- **영향 범위:** 사용자 onboarding과 운영 가이드

### E. CLI 검증과 npm 배포 분리
- **관련 위치/대상:** `.github/workflows/openlog-cli-publish.yml`
- **변경 전 상황:** CLI 파일이 변경된 모든 PR에서 현재 package version이 npm에 이미 배포됐는지 검사해, 릴리스 목적이 아닌 변경에도 매번 version bump가 필요했습니다.
- **변경한 내용:** PR에서는 test/build/package 검증만 수행하고, npm version 중복 검사는 `develop`의 publish job에서만 수행하도록 변경했습니다.
- **변경 후 동작:** 이미 배포된 version이면 publish를 정상적으로 생략하며, version이 실제로 변경된 경우에만 npm에 배포합니다.
- **구현 흐름:**
  1. PR의 `verify` job이 CLI 테스트, 빌드, 패키지 구성을 검증합니다.
  2. publish job은 package version이 npm에 없을 때만 `npm publish`를 실행합니다.
- **바뀌는 데이터/상태:** package version 변경이 명시적인 릴리스 신호가 됩니다.
- **영향 범위:** CLI PR 검증과 `develop` 자동 배포

## 5. 테스트 및 검증 방법
- **검증 환경:** Java 21/Gradle, Node.js/npm, pnpm, PostgreSQL 16 Docker, Playwright Chromium
- **검증한 시나리오:**
  - Backend 관련 테스트와 Kotlin compile
  - CLI build 및 성공·취소·rollback·remote 없음 등을 포함한 50개 테스트
  - Frontend lint/build와 Agent Settings E2E 3개 시나리오
  - CLI workflow YAML 파싱과 이미 배포된 package version의 publish 생략 경로
  - PostgreSQL 16에서 기존 workspace repository migration, 중복 repository 정규화, 기본 Guide·Capture Mode 생성, legacy column 제거
  - read-only 권한에서 context 조회와 write Tool 미노출
- **확인한 결과:**
  - `./gradlew :backend:test :backend:compileKotlin` 성공
  - `packages/openlog-cli`: `npm run build`, `npm test` 성공(50 passed)
  - `npm pack --dry-run`과 CLI workflow YAML 파싱 성공
  - `frontend`: `pnpm lint` 성공(오류 0, 기존 경고 14), `pnpm build` 성공
  - `pnpm exec playwright test e2e/agent-settings.spec.ts` 성공(3 passed)
  - PostgreSQL migration 검증 결과 Guide 3건, 중복 제거된 Project 1건, 기본 `ASK`, legacy column 제거 확인
  - 저장소 루트에는 `package.json`이 없어 템플릿의 `npm run preflight`는 실행할 수 없었고, 위 구성요소별 검증으로 대체했습니다.
- **확인하지 못한 부분:** Codex·Claude Code·Cursor 실제 클라이언트에서 MCP initialize instructions를 따른 `start_openlog_session` 자동 호출 여부는 수동 검증이 필요합니다.
