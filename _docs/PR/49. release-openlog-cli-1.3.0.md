## 2. 변경 배경 및 목표
- **변경 전 상태:** `develop`에는 `openlog init`, MCP instructions, `start_openlog_session`이 포함돼 있지만 CLI package version과 npm `latest`는 모두 `1.2.1`입니다.
- **문제/필요성:** `npx -y @openloghq/cli@latest init`은 배포된 1.2.1을 실행하므로 새 명령을 인식하지 못하고, 배포된 MCP에서도 새 session Tool을 사용할 수 없습니다.
- **이번 PR의 목표:** CLI package version을 `1.3.0`으로 변경해 새 CLI와 MCP 구현을 배포하고, 이후 CLI 변경은 수동 version bump를 빠뜨려도 npm 최신 버전 다음 patch로 자동 배포되도록 합니다.

## 3. 주요 구현 내용 및 동작 방식

### A. OpenLog CLI 1.3.0 릴리스 준비
- **관련 위치/대상:** `packages/openlog-cli/package.json`, `packages/openlog-cli/package-lock.json`
- **변경 전 상황:** package와 lockfile의 root version이 이미 배포된 `1.2.1`이었습니다.
- **변경한 내용:** 새 CLI 명령과 MCP 기능 추가를 반영해 package version을 SemVer minor release인 `1.3.0`으로 맞췄습니다.
- **변경 후 동작:** develop merge 시 CLI workflow가 npm에서 미배포 버전을 확인하고 `@openloghq/cli@1.3.0`을 publish합니다.
- **구현 흐름:**
  1. PR에서 CLI test, build, package contents를 검증합니다.
  2. merge 후 develop publish job이 `1.3.0`의 미배포 상태를 확인하고 npm publish를 실행합니다.
- **바뀌는 데이터/상태:** npm package version과 `latest` dist-tag가 배포 완료 후 `1.3.0`으로 변경됩니다.
- **영향 범위:** `npx @openloghq/cli@latest`, 전역 MCP 설정이 실행하는 OpenLog CLI/MCP 버전

### B. npm 최신 버전 기반 자동 릴리스
- **관련 위치/대상:** OpenLog CLI publish workflow, release version resolver와 테스트
- **변경 전 상황:** package version이 이미 npm에 배포돼 있으면 publish job이 성공으로 종료되며 배포를 생략했습니다. CLI 기능 merge와 version bump가 별도 수동 작업이라 새 기능이 npm `latest`에 포함되지 않을 수 있었습니다.
- **변경한 내용:** publish job이 npm 최신 버전과 source의 요청 버전을 비교해 실제 릴리스 버전을 결정하도록 변경했습니다. 요청 버전이 더 높으면 minor/major 버전을 유지하고, 같거나 낮으면 npm 최신 patch를 자동 증가시킵니다.
- **변경 후 동작:** CLI package 변경이 develop에 merge되면 항상 미배포 버전이 계산되어 publish됩니다. 수동 workflow 배포는 develop에서만 허용하고 모든 npm publish job은 전역 직렬화합니다.
- **구현 흐름:**
  1. npm `latest`와 package의 요청 버전을 조회합니다.
  2. 명시된 상위 버전 또는 npm 최신 다음 patch를 선택합니다.
  3. 필요하면 runner에서 package version을 갱신한 뒤 build, pack, publish를 수행합니다.
- **바뀌는 데이터/상태:** 수동 version bump는 minor/major 릴리스 선택 수단으로 유지되며, 누락 시 patch 릴리스가 자동 생성됩니다.
- **영향 범위:** CLI PR 검증, develop 자동 배포, workflow dispatch, npm publish 동시성
