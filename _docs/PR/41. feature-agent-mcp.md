## 2. 변경 배경 및 목표
- **변경 전 상태:** OpenLog MCP는 계정·게시글·이미지와 working brief 중심의 일부 tool만 제공했다. 모든 tool이 동일하게 노출됐고 로컬 에이전트가 실행 가능한 읽기·쓰기·삭제 범위를 구분하는 설정이 없었다.
- **문제/필요성:** 에이전트가 Workspace의 Task, Log, Todo, Memory, Output, Graph link를 다루려면 REST API를 MCP tool로 확장해야 한다. 동시에 사용자가 허용한 범위보다 강한 변경·삭제 tool이 노출되지 않도록 로컬 안전 정책이 필요하다.
- **이번 PR의 목표:** Workspace API를 permission-aware MCP tool로 제공하고, `read-only`, `safe-write`, `full` 프로필로 tool 등록 범위를 제어한다. 발행 작업은 기존 확인 절차를 유지하고 삭제 작업은 `full` 프로필에서만 허용한다.

## 3. 주요 구현 내용 및 동작 방식

### A. 로컬 MCP 권한 프로필 추가
- **관련 위치/대상:** `mcp-permissions.ts`, `mcp-permissions-command.ts`, `config.ts`, `index.ts`, `mcp-install.ts`
- **변경 전 상황:** MCP server가 제공하는 tool 범위를 사용자가 로컬에서 제한할 방법이 없었다.
- **변경한 내용:** `read-only`, `safe-write`, `full` 프로필과 `read`, `write`, `publish`, `delete` capability를 추가했다. `openlog mcp permissions show|set|reset` 명령과 `OPENLOG_MCP_CONFIG_FILE` 경로 재정의를 제공한다.
- **변경 후 동작:** 설정 파일이 없으면 기존 쓰기 동작과 호환되는 `safe-write`를 사용한다. 프로필 변경 후 MCP server를 재시작하면 허용되지 않은 tool은 `tools/list`에 등록되지 않는다.
- **구현 흐름:**
  1. CLI가 `~/.openlog/mcp-config.json`에서 프로필을 읽고 형식과 갱신 시각을 검증한다.
  2. 파일이 없으면 `safe-write`, 설정이 있으면 선택한 프로필의 capability를 계산한다.
  3. MCP server는 시작할 때 capability에 맞는 tool만 등록한다.
- **바뀌는 데이터/상태:** 권한 설정 파일은 `0600` 모드로 저장되며 profile, version, updatedAt을 포함한다.
- **영향 범위:** OpenLog CLI 명령, MCP client 설치 환경 변수, MCP tool 노출 범위.

### B. capability 기반 MCP tool registry 분리
- **관련 위치/대상:** `mcp-toolkit.ts`, `mcp-server.ts`
- **변경 전 상황:** tool 등록, 인증 client 생성, 오류 응답 변환, tool annotation 처리가 하나의 server 파일에 반복돼 있었다.
- **변경한 내용:** 인증형·로컬 tool 등록을 `McpToolRegistry`로 분리하고 read/write/idempotent/delete annotation과 공통 text/error 응답을 추가했다. 등록 시점과 실행 직전에 capability를 각각 확인한다.
- **변경 후 동작:** 허용되지 않은 tool은 목록에 나타나지 않고, 이미 획득한 callback을 우회 호출해도 MCP `isError` 응답으로 거부된다. API와 인증 오류는 throw 대신 MCP 표준 오류 결과로 정규화된다.
- **영향 범위:** 모든 MCP tool 등록, 권한 검사, 인증 오류와 API 오류 응답.

### C. Workspace MCP tool 확장
- **관련 위치/대상:** `mcp-workspace-tools.ts`, `mcp-server.ts`, `api-client.ts`
- **변경 전 상황:** Workspace에서는 working brief 갱신만 가능했고 Task, Log, Todo, Memory, Output, Activity, Graph link API를 에이전트가 사용할 수 없었다.
- **변경한 내용:** Workspace 조회·활동, working brief, Task, Log, Todo, Memory, Output, 관계 link의 조회·생성·수정·삭제 tool을 추가했다. 날짜·ID·상태·관계 enum을 Zod로 검증하고 API client에 PATCH, DELETE, 빈 성공 응답 처리를 추가했다.
- **변경 후 동작:**
  - `read-only`: 계정과 Workspace 데이터 조회
  - `safe-write`: 조회, 생성·수정, 관계 연결, todo 완료, 확인 후 게시글·Output 발행
  - `full`: `safe-write`와 개별 삭제, working brief 초기화
- **구현 흐름:**
  1. 입력 schema가 양수 ID, ISO 날짜와 범위, API enum을 MCP 호출 전에 검증한다.
  2. registry가 capability를 검사하고 인증된 API client로 REST 요청을 수행한다.
  3. 게시글과 Output 발행은 기본적으로 preview를 반환하고 명시적인 확인 값이 있을 때만 POST한다.
- **바뀌는 데이터/상태:** 허용된 프로필에서 Workspace 문서와 관계가 생성·수정·삭제되며 publish 요청은 확인 후 공개 상태를 만든다.
- **영향 범위:** OpenLog Workspace 전체 API, MCP tool schema와 실행 결과.

### D. 문서와 Vercel 변경 감지 설정 갱신
- **관련 위치/대상:** `README.md`, `README.ko.md`, `packages/openlog-cli/README.md`, `frontend/vercel.json`
- **변경 전 상황:** 문서에 권한 프로필과 확장된 Workspace tool이 없었고 Backend·CLI 전용 커밋에서도 Vercel이 Frontend build를 시작할 수 있었다.
- **변경한 내용:** 영문·한글 README에 권한 명령, 프로필별 capability, tool 그룹과 환경 변수를 문서화했다. Frontend 경로 변경이 없는 커밋은 Vercel build를 건너뛰도록 `ignoreCommand`를 추가했다.
- **변경 후 동작:** 사용자는 권한 프로필과 tool 범위를 문서에서 확인할 수 있고 Frontend와 무관한 커밋은 불필요한 Vercel build를 실행하지 않는다.
- **영향 범위:** CLI/MCP 사용자 문서, Vercel Frontend 배포 감지.

## 5. 테스트 및 검증 방법
- **검증 환경:** macOS, Node.js 25.2.1, TypeScript 6.0.3

## 6. 리뷰어 참고 사항 (선택)
- **리뷰할 때 봐야 할 점:** `safe-write`는 기존 사용성과 호환하기 위한 기본값이다. 발행은 별도 `publish` capability와 확인 값이 필요하고, 삭제는 `full`에서만 등록된다. 로컬 프로필과 별개로 Backend의 사용자 인증·소유권 검사는 계속 적용된다.
- **영향 범위:** MCP server를 재시작할 때 읽는 로컬 권한 파일과 해당 프로필의 tool 목록.
