## 2. 변경 배경 및 목표
- **변경 전 상태:** 운영 Backend와 PostgreSQL, Redis, Kafka, Debezium, Nginx는 GCP VM에서 실행됐고 미디어는 GCS에 저장됐다. 운영 인프라와 배포 workflow도 GCP의 AMD64 VM과 GCS 인증 방식을 전제로 구성됐다.
- **문제/필요성:** GCP 운영 종료 전에 ARM64 기반 OCI VM과 OCI Object Storage로 서비스를 이전해야 한다. 새 VM을 재현 가능하게 설정하고, 기존 GCS 동작을 유지하면서 운영 환경별로 저장소 구현을 선택할 수 있어야 한다.
- **이번 PR의 목표:** 기존 OCI 리소스를 Terraform으로 관리하고 Ansible로 VM을 프로비저닝한다. Backend에 OCI Object Storage 구현을 추가하고, 데이터 이전과 ARM64 배포에 필요한 스크립트 및 CD 설정을 제공한다.

---

## 3. 주요 구현 내용 및 동작 방식

### A. OCI 운영 인프라 Terraform 편입
- **관련 위치/대상:** `infra/terraform/oci/production/`
- **변경 전 상황:** OCI VM, VCN, subnet, security list가 콘솔에서 생성된 상태였고 Object Storage bucket, instance principal IAM, 원격 Terraform state 구성이 없었다.
- **변경한 내용:** 기존 VM과 네트워크 리소스를 import할 Terraform 구성을 추가했다. 미디어 및 state bucket, dynamic group, Object Storage IAM policy를 선언하고 OCI native backend를 구성했다.
- **변경 후 동작:** 운영 OCI 리소스와 Terraform state가 일치하며, VM과 bucket에는 `prevent_destroy`가 적용된다. VM은 instance principal로 별도 API key 없이 미디어 bucket을 관리한다.
- **구현 흐름:**
  1. `bootstrap.sh`가 기존 OCI 리소스 ID를 조회해 변수 파일을 만들고 state bucket을 준비한다.
  2. 기존 네트워크와 VM을 Terraform state로 import한다.
  3. Terraform이 미디어 bucket과 instance principal IAM을 관리한다.
- **바뀌는 데이터/상태:** Terraform state가 OCI Object Storage의 `openlog/production/terraform.tfstate`에 저장된다.
- **영향 범위:** OCI VM, VCN, subnet, security list, Object Storage, IAM, Terraform 실행 환경.

### B. Ansible 기반 OCI VM 프로비저닝
- **관련 위치/대상:** `infra/ansible/`
- **변경 전 상황:** OCI VM은 OS만 설치된 상태였고 Docker, 방화벽, 배포 계정과 운영 디렉터리를 수동으로 준비해야 했다.
- **변경한 내용:** Ubuntu 22.04 검증, Docker Engine/Compose 설치, Docker log rotation, SSH key 등록, `/opt/openlog` 디렉터리 생성, UFW 22/80/443 허용을 수행하는 playbook을 추가했다.
- **변경 후 동작:** 동일 playbook을 반복 적용해도 추가 변경이 발생하지 않으며 VM 설정을 코드로 재현할 수 있다.
- **영향 범위:** OCI 운영 VM의 패키지, Docker daemon, SSH 접근, OS 방화벽과 배포 디렉터리.

### C. GCS/OCI 미디어 저장소 추상화
- **관련 위치/대상:** `backend/src/main/kotlin/io/github/kitae9999/openlog/media/`, `backend/build.gradle.kts`
- **변경 전 상황:** `MediaService`가 Google Cloud Storage SDK에 직접 의존해 GCS signed URL과 객체 이동·삭제를 처리했다.
- **변경한 내용:** `MediaStorage` 인터페이스와 GCS 구현을 분리하고 OCI Object Storage 구현을 추가했다. OCI 구현은 instance principal 인증과 객체 단위 Pre-Authenticated Request를 사용한다.
- **변경 후 동작:** `MEDIA_STORAGE_PROVIDER`에 따라 `gcs` 또는 `oci` 구현이 선택된다. 기존 환경은 기본값 `gcs`로 동일하게 동작하고 OCI 환경은 API key 없이 업로드·조회 URL과 객체 작업을 처리한다.
- **구현 흐름:**
  1. `MediaService`가 provider 공통 인터페이스로 업로드, 조회, 존재 확인, 이동, 삭제를 요청한다.
  2. Spring 조건부 bean이 운영 환경에 맞는 저장소 구현을 선택한다.
  3. OCI VM은 instance principal IAM으로 Object Storage 요청을 인증한다.
- **바뀌는 데이터/상태:** OCI 복원 시 `media_assets.bucket` 값이 `openlog_prod`에서 `openlog-media`로 변경된다. 객체 key와 `/api/media/assets/{UUID}` 경로는 유지된다.
- **영향 범위:** 미디어 업로드 URL 발급, 미디어 조회 redirect, 업로드 완료 확인, 게시글 첨부 객체 이동, orphan 객체 정리.

### D. 데이터 이전 및 ARM64 배포 경로 추가
- **관련 위치/대상:** `deploy/migration/`, `deploy/production/production.env.example`, `.github/workflows/backend-cd.yml`
- **변경 전 상황:** 운영 DB와 GCS 객체를 OCI로 옮기는 반복 가능한 절차가 없었고 Backend CD는 단일 플랫폼 이미지만 생성했다.
- **변경한 내용:** GCS 객체 동기화·검증, GCP PostgreSQL custom dump 전송, OCI DB 복원 및 bucket 값 변환, OCI 환경 변수 적용 스크립트를 추가했다. CD는 Buildx로 `linux/amd64`와 `linux/arm64` 이미지를 함께 발행한다.
- **변경 후 동작:** 최종 전환 시 GCP 쓰기를 중단한 뒤 동일 스크립트로 미디어와 DB를 재동기화할 수 있다. 복원 스크립트는 OCI의 Nginx, Backend, Debezium을 정지하고 복원한 다음 전체 stack과 health endpoint를 확인한다.
- **바뀌는 데이터/상태:** GCS 객체가 OCI media bucket에 복제되고 PostgreSQL dump가 OCI DB에 복원된다. CD image manifest에 AMD64와 ARM64가 포함된다.
- **영향 범위:** 운영 데이터 이관, Backend container build, GitHub Actions production deploy.

## 5. 테스트 및 검증 방법
- **검증 환경:** macOS ARM64, Java 21, Terraform 1.15, OCI Tokyo ARM64 VM(Ubuntu 22.04), GCP 운영 VM
- **검증한 시나리오:**
  - Backend 전체 테스트와 bootJar 생성
  - OCI Terraform format, validate, 실제 state refresh 및 plan
  - Ansible syntax와 OCI VM 반복 적용 멱등성
  - migration shell script 구문 검사
  - GCP/OCI PostgreSQL 핵심 테이블 실제 행 수 비교
  - GCS/OCI 객체 이름 비교 및 OCI Pre-Authenticated Request 미디어 조회
  - DNS 변경 없이 OCI Nginx HTTPS와 `/healthz` 확인
- **확인한 결과:**
  - `./gradlew :backend:test :backend:bootJar` 성공
  - `terraform validate` 성공, `terraform plan -detailed-exitcode` 결과 `No changes`
  - Ansible 결과 `changed=0`, `failed=0`
  - migration script `bash -n` 성공
  - GCP/OCI 핵심 테이블 count 일치 및 OCI DB 전체 문자열 컬럼에 GCS bucket/직접 URL 잔존값 없음
  - OCI 미디어 조회 HTTP 200, `/healthz` 응답 `ok`
- **확인하지 못한 부분:** GitHub production secret을 OCI 값으로 변경한 뒤 실행되는 실제 CD와 Cloudflare 원본 전환은 PR 병합 후 검증해야 한다.
